🛡️ P2P Alert Guard

In Nigerian P2P crypto trades, scammers send fake bank-alert screenshots and wait for the seller to release USDT. This agent checks the payment with Paystack itself over a Reclaim zkTLS connection, decides APPROVE_RELEASE or REJECT, and puts a Groth16 receipt of that decision on zkVerify.

Try a scenario:

Tip: after an approval, press “Check” again with a different trade ID — the same alert can't release crypto twice (REFERENCE_REUSED).

How it works

  1. The seller (or their bot) sends the buyer's claim: reference + amount.
  2. The guard calls GET api.paystack.co/transaction/verify/:reference through Reclaim zkFetch. The seller's Paystack secret key is a private header: used inside TLS, never in the proof.
  3. The zkTLS proof reveals only status, amount, currency, reference, mode and Paystack transaction id; customer details stay redacted.
  4. Deterministic policy: APPROVE only if status = success, amount is exact, currency = NGN, and the reference was never used to release before (Redis). Anything else, or any error, is a REJECT.
  5. A Groth16 circuit recomputes the decision from those facts, bound to the Reclaim proof ID, and the proof is submitted to zkVerify.

API: POST /check {"reference","expected_amount_ngn","trade_id?","payee?"} · /health · source & README

Demo runs on Paystack test mode (no real money). zkTLS proofs are rationed (free Reclaim tier), so repeat checks reuse a cached proof.
